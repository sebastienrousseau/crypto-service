# Conformance kit

Request and response vectors for the crypto-server REST API, for SDKs
and clients written in other languages. Run them against a server, in
order, file by file: an SDK that passes every vector sends what the
server expects and reads what it answers. The contract they test is
[`openapi/crypto-service.openapi.yaml`](../openapi/crypto-service.openapi.yaml);
crypto-server runs the same vectors in its own test suite
(`packages/crypto-server/__tests__/conformance.test.ts`, the reference
runner).

## Files

| File              | Covers                                                         |
| :---------------- | :------------------------------------------------------------- |
| `meta.json`       | `GET /`, algorithm catalogue, DORA and CBOM documents          |
| `probes.json`     | `/health`, `/live`, `/ready`, `/metrics` (no credentials)      |
| `hash.json`       | `/v2/hash`, every algorithm                                    |
| `mac.json`        | `/v2/hmac`, `/v2/hmac/verify`                                  |
| `kdf.json`        | `/v2/kdf`, `/v2/password/hash`, `/v2/password/verify`          |
| `symmetric.json`  | AEAD, secretbox, password encryption, AES key wrap             |
| `signing.json`    | server-held Ed25519 keys, batch signing, export, delete        |
| `asymmetric.json` | sealed boxes, ML-KEM, hybrid KEM, multi-recipient, streams     |
| `pq-sign.json`    | ML-DSA, SLH-DSA, ISO 20022 dual signatures                     |
| `hpke.json`       | HPKE with X25519 and X-Wing keys                               |
| `kms.json`        | KMS routes on the local provider                               |
| `opaque.json`     | OPAQUE error contract                                          |
| `errors.json`     | 401, 403, validation, malformed input, unknown key and route   |
| `v1.json`         | deprecated OpenPGP routes                                      |
| `SHA256SUMS`      | `sha256sum` of every other file, checked by the reference test |

Every key in the kit is synthetic. Files hold public keys and signatures
only; key pairs the vectors need are generated by the server under test.

## Server

The vectors assume a server started with:

- `JWT_SECRET` set (32 bytes or more), with `JWT_ISSUER` and
  `JWT_AUDIENCE` if the runner's tokens carry `iss` and `aud`;
- `RATE_LIMIT_MAX` high enough for a file's requests (the default is 10
  a minute per address);
- `KMS_PROVIDERS` unset or `local`, and the docs and v1 routes on (the
  defaults).

The tenant quota is 60 requests a minute per principal, so each file runs
as its own principal: `sub` is `conformance-<group>`, and no file sends
more than 60 requests.

## Vector files

Each file is a JSON object:

```json
{
  "group": "hash",
  "description": "What the file covers.",
  "vectors": [
    {
      "id": "hash-sha256-abc",
      "description": "What the vector shows.",
      "auth": "admin",
      "request": {
        "method": "POST",
        "path": "/v2/hash",
        "body": { "algorithm": "sha256", "data": "abc" }
      },
      "expect": {
        "status": 200,
        "mediaType": "application/json",
        "body": {
          "data": { "digest": "ba7816bf…", "algorithm": "sha256", "length": 32 }
        }
      },
      "capture": { "digest": "/data/digest" }
    }
  ]
}
```

Run the vectors of a file in order, on one server, keeping the captured
values for the rest of the file.

### `auth`

- `"admin"` (the default when absent): a Bearer JWT whose `scopes` is
  `["crypto:admin"]`. The API key holds the same scopes and may be used
  instead.
- `{"scopes": [...]}`: a Bearer JWT with exactly those scopes.
- `"none"`: no `Authorization` or `x-api-key` header.

Tokens are HS256, signed with `JWT_SECRET`, with `sub` as above, `iat`
now and `exp` within `JWT_MAX_AGE` (default 3600 s).

### `request`

- `method`, `path`: the HTTP method and path, no query string.
- `body`: a JSON value, sent as `application/json`.
- `rawBody`: sent as it is, with the media type in `headers` (malformed
  input vectors).
- `headers`: extra request headers. Credentials never appear here.

### `expect`

- `status`: the HTTP status.
- `mediaType`: the `Content-Type` without parameters. Errors are
  `application/problem+json` (RFC 9457).
- `headers`: response headers that must have exactly these values.
- `body`: a template the parsed JSON body must match, or `text` for a
  non-JSON body.

A template matches as follows:

- strings, numbers, booleans and `null` match exactly;
- arrays match element by element and must have the same length;
- objects must have exactly the template's members (none missing, none
  extra), each matching;
- an object whose only member is `$shape` matches any value its JSON
  Schema (2020-12) accepts. It stands for values that differ from run to
  run (ciphertexts, key IDs, timestamps).

### Substitution and `capture`

`capture` maps a name to a JSON pointer (RFC 6901) into the response
body; the value there is kept as a string. Any later string in the same
file, in a request or in a template, may contain `${name}`, replaced
with the captured value before use. This is how a key generated by the
server is used by the next vector, and how a round trip is checked
exactly (the shared secret decapsulated equals the one encapsulated).

## Encodings

The response schemas name each string's encoding, and the vectors
depend on it:

- keys, signatures, digests, MACs, shared secrets, KEM ciphertexts and
  HPKE output: lowercase hex;
- AEAD, secretbox, sealed-box, stream, password-encryption and AES-KW
  outputs: standard base64 with padding;
- decrypted plaintexts: UTF-8 text (invalid sequences become U+FFFD);
  `/v2/hpke/open` and `/v2/kms/decrypt` also return the bytes as `hex`;
- KMS ciphertexts and wrapped keys: opaque provider strings, passed back
  unchanged.

Behaviour an SDK must not guess:

- `/v2/secretbox/open`, `/v2/sealedbox/open`, `/v2/sealedbox/open-pq`,
  `/v2/password/decrypt` and `/v2/keys/unwrap` answer `data` as a bare
  string, not an object;
- `/v2/hpke/seal` treats `plaintext`, `info` and `aad` as hex when they
  are an even-length hex string, as UTF-8 text otherwise;
- `/v2/kms/encrypt` reads `plaintext` as UTF-8 unless `encoding` is
  `hex`;
- `GET /` and `GET /v2/compliance/cbom` are not wrapped in `data`;
- unknown request members are removed before validation, not refused;
- a body that fails validation is a 400 `validation-failed` with
  `errors[]`; the server never answers 422.

## Provenance of exact values

- Digests, HMACs, HKDF, PBKDF2, scrypt and the Argon2id hash in
  `kdf.json`: Node's `crypto` (OpenSSL), independent of crypto-lib;
  BLAKE3 from the BLAKE3 reference test vectors.
- HMAC inputs: RFC 4231 test case 1. AES-KW and AES-KWP: RFC 3394
  section 4.1 and RFC 5649 section 6. Ed25519: RFC 8032 section 7.1,
  TEST 2.
- Fixed XChaCha20-Poly1305 ciphertexts: `@noble/ciphers` with a fixed
  nonce; the password envelope, ISO 20022 envelope and OpenPGP message:
  crypto-lib and OpenPGP.js with synthetic keys.

## Changing the kit

Edit the JSON, format it as the pre-commit hook will (it runs Prettier
on every staged `.json` and `.md`, which would otherwise change the files
after their checksums were taken), then update the checksums from this
directory:

```sh
pnpm exec prettier --write *.json README.md
sha256sum *.json README.md > SHA256SUMS
```

`pnpm --filter @sebastienrousseau/crypto-server test` runs every vector
and checks `SHA256SUMS`.
