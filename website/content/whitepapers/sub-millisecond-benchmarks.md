<div class="whitepaper-doc-abstract">
<h3>Status</h3>
<p>
This paper previously reported latency and throughput figures (ML-KEM-768 encapsulation in 34.1 µs, ML-DSA-65 verification in 68.4 µs, more than 100,000 operations per second, zero garbage-collection pauses) attributed to a WebAssembly SIMD core. Those figures were not produced by any committed benchmark code, and <code>@sebastienrousseau/crypto-wasm</code> contains no WebAssembly. They have been withdrawn.
</p>
<p>
All post-quantum operations in Crypto Service Suite run in JavaScript through <code>@noble/post-quantum</code>, which is not independently audited, does not guarantee constant-time execution, and is not a validated cryptographic module. No latency figures are published until they are generated by the committed benchmark code with the environment recorded.
</p>
</div>

<section id="reproducibility" class="research-section">
<h2>2. Running the Benchmarks</h2>
<p>
The repository contains two benchmark entry points. The script <code>benchmarks/crypto-bench.ts</code> times crypto-lib operations, including ML-KEM-768 key generation and encapsulation and ML-DSA-65 key generation. The <code>@sebastienrousseau/crypto-benchmarks</code> harness times ML-KEM-768 encapsulation and ML-DSA-65 verification through crypto-lib against a P-256 ECDH baseline.
</p>
<pre><code>git clone https://github.com/sebastienrousseau/crypto-service.git
cd crypto-service
pnpm install
pnpm -r run build
node benchmarks/crypto-bench.ts --iterations 500</code></pre>
<p>
Record the Node.js version, operating system, CPU and iteration count with any result, run on an otherwise idle machine, and repeat several times. Results depend on hardware and load and are not service level guarantees.
</p>
